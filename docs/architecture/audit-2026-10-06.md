# System Architecture & Best Practices Audit

**Repo:** `vitrixLab/social-media-smm-automation`
**Branch:** `dev` @ `06ce31b`
**Stack (actual, verified):** Next.js 16.3.6 (App Router) + TypeScript (strict) + Prisma 7/Neon Postgres + Tailwind v4, alongside a separate Python 3.11/FastAPI codebase. No GraphQL. Deployment target for the dashboard is Vercel (per repo docs) with Netlify reported working for a different part of the project.

I have direct read/write access to this repository and ran its actual build, lint, audit, and CLI tooling rather than inferring from commit messages — every claim below is either a file/line reference or a command you can re-run yourself. I did not need to request files from you; where something was genuinely unverifiable from the repo alone (e.g., production runtime behavior, actual Vercel/Netlify project settings), I've said so explicitly instead of guessing.

## 1. Executive Summary

**Health score: 3/10** — appropriate for "active development, pre-launch," but the number reflects a specific, narrow problem, not a hopeless codebase: **the thing that deploys cannot currently build**, and the feature that got the most recent dedicated engineering effort (CRM/client persistence) is both fake and unreachable from the UI at the same time. That combination — broken *and* disconnected — is why this scores lower than "has bugs."

What's actually good here, stated plainly so the rest of this report isn't read as uniformly damning: TypeScript strict mode is on and the Prisma schema design itself is reasonable (proper relations, sensible fields). Accessibility semantics in the main dashboard header are genuinely well done — `aria-label`, `aria-expanded`, `aria-pressed`, `role="group"` are used correctly and consistently, which is more than a lot of pre-launch products get right. There's a real CI pipeline. None of this is a greenfield mess; it's a codebase where real engineering happened, repeatedly, without anyone verifying the result compiled before the next layer was added on top.

The core finding, in one sentence: **this repo contains three products (a static site, a Python automation engine, and a Next.js dashboard) that don't talk to each other, and the one that's live-facing currently fails its own build.**

## 2. Critical Issues (P0)

These block core functionality, stability, or security. Fix before anything else matters.

1. **The dashboard does not build.** `pnpm build` fails TypeScript compilation with 50+ errors (full output in §5.2). `next.config.ts` has no `ignoreBuildErrors` escape hatch, so this fails identically on any platform that runs a real `next build`.
2. **"Persistence" is fake.** The most recent commit claims PostgreSQL/Neon integration. `src/lib/prisma.ts` and `src/generated/prisma/index.ts` are hand-written stub files, not `prisma generate` output — every call returns `null`/`[]`/a hardcoded object regardless of what's passed in. Nothing a user creates in the CRM survives a page refresh, once the build even succeeds.
3. **The built CRM "Clients" feature is unreachable.** `ClientsTable.tsx`, `ClientForm.tsx`, `ClientStatsCards.tsx` are complete, working components. `dashboard/page.tsx`'s `clients` case renders a static placeholder paragraph instead of them (`src/app/dashboard/page.tsx:88-95`). The feature exists and is dead code simultaneously.
4. **No authentication is enforced anywhere.** `/api/auth/login` is an honestly-labeled demo stub (hardcoded `admin@smmai.com`/`admin`), but nothing checks it — there is no `middleware.ts` in the project, and `dashboard/page.tsx` never reads the stored token. `/dashboard` and every `/api/crm/*` route, including the dry-run safety toggle, are open to anyone with the URL.
5. **The dry-run safety toggle doesn't reliably persist.** `src/app/api/crm/status/route.ts` stores `dryRun`/`wasmRanking` in a module-level `let`. This is not guaranteed to survive between serverless invocations or across concurrent instances. The one flag standing between simulated and live posting is currently unreliable by construction.

## 3. Architecture Review

### Current state

```
vitrixLab/social-media-smm-automation
│
├── index.html, login.html, style.css        Static site (root)
│
├── src/smm/  (Python / FastAPI)               Real, tested (pytest + ruff in CI),
│   domain/ adapters/ moderation/ workflows/    documented architecture. No live HTTP
│   main.py  ([tool.vercel] entrypoint)         deployment path — no api/ dir, no
│                                                vercel.json builds. Zero HTTP link to
│                                                the dashboard below. CI (.github/
│                                                workflows/ci.yml) only runs pytest/ruff
│                                                against this half of the repo.
│
└── nextjs-setup/nextjs-dashboard/  (Next.js)   What's actually meant to go live.
    ├── src/app/dashboard/                       Three independent nav components (§4).
    ├── src/app/api/crm/*                         Currently fails to build.
    ├── prisma/                                    Real schema, fake client.
    └── src/components/{layout,crm}/               Not covered by CI at all.
```

Three systems, one repo, zero integration between them, and CI that exercises exactly one of the three. A contributor merging to `dev` today gets a green check from CI regardless of whether the Next.js app builds, because CI never tries.

### Coupling & single points of failure

- **No circular dependencies found** — the module graph within the Next.js app is acyclic; `src/lib/crm.ts` is correctly positioned as a leaf dependency for types.
- **The real coupling problem is the opposite of circular: total decoupling where there should be a contract.** The Python engine and the Next.js dashboard both model "content drafts" and "publishing," independently, with no shared schema or API boundary between them. If both are meant to be the same product, this is two parallel, divergent implementations of the same domain.
- **Single point of failure:** `src/lib/prisma.ts` is imported by every CRM API route. Right now it's a no-op stub, so the "failure" is silent (everything *looks* like it works and returns 200s) rather than loud — arguably worse than a hard dependency failure, because nothing alerts anyone.

### Environment configuration & secrets

- `.env.example` lists `AI_PROVIDER`, `DRY_RUN`, `META_ACCESS_TOKEN`, `META_PAGE_ID`, `DATABASE_URL`, `DIRECT_URL`. `.gitignore` correctly excludes `.env`/`.env*.local`.
- No hardcoded secrets found repo-wide (checked via pattern grep across `.ts`/`.tsx`/`.py`/`.json`/`.md`) — the only credential-shaped string in the codebase is the already-documented demo login token generator, not a real secret.
- None of `DATABASE_URL`/`DIRECT_URL`/`META_ACCESS_TOKEN`/etc. are actually referenced anywhere in the Next.js source (`process.env.*` grep across `src/` returns zero matches outside what Prisma reads internally) — meaning the Meta integration env vars are currently decorative; there's no code path that uses them.

### Ideal target (recommended)

Pick one of two shapes on purpose, rather than letting the current accidental split stand:

- **Option A — dashboard-only product.** Drop the Python engine from this deployment's scope entirely (or keep it as an internal CLI/library, documented as such). The Next.js app becomes self-contained: its own Prisma-backed content model, its own publish logic. Simplest to ship.
- **Option B — dashboard as a UI over the real engine.** The Next.js app's `/api/crm/drafts` and `/api/crm/publish` routes call into the Python engine over HTTP (requiring an actual Vercel Python function or a separately-hosted FastAPI service) instead of maintaining a second, parallel Postgres content model.

Neither is implemented today. The current code behaves like Option A (self-contained Postgres model) while the docs and README describe Option B's engine as "the" product. Decide, then update `README.md` to say which.

## 4. Frontend Deep Dive

### Header (`src/components/layout/DashboardHeader.tsx`)

Semantic structure is reasonable — real `<button>` elements for controls, `role="group"` with `aria-label` on button clusters (view-mode, density toggles), `aria-pressed` on toggle states, `aria-expanded` on the sidebar/notification/user-menu disclosure buttons. This is correctly implemented, not just present:

```tsx
<button
  onClick={onToggleSidebar}
  aria-label={sidebarOpen ? "Close sidebar" : "Open sidebar"}
  aria-expanded={sidebarOpen}
  ...
>
```

Two real problems in the same file:

- **The notification panel shows hardcoded content**, not live data: `<li>3 drafts awaiting approval</li>`, `<li>New client added — Northwind Labs</li>` are literal strings, not derived from `notificationCount` or any data source. A user will see the same two "notifications" forever.
- **The header is also where the three-way navigation duplication lives** (full detail in the architecture review from earlier work in this audit): `DashboardHeader`'s tab set, `DashboardShell`'s sidebar `navItems`, and `LayoutControlBar`'s `sections` each define a different list of dashboard sections, all bound to one shared `currentSection` state. Concretely: `Overview`, `Drafts`, and `Settings` are tabs in the header that render nothing when clicked, because `dashboard/page.tsx`'s content switch has no matching case for them.

### Icons

**No icon library is installed** (`package.json` has no `lucide-react`, `react-icons`, `@heroicons/react`, or similar). Every icon in the app is a hand-written inline `<svg>` — at least seven separate inline SVG blocks in `DashboardHeader.tsx` alone, each a one-off copy rather than a shared `<Icon name="..." />` component. Sizes are inconsistent even within the same file and same visual row: `width="18"`, `width="16"`, `width="14"` appear for icons sitting in comparable UI contexts, with no apparent system behind the choice. This isn't an accessibility problem (every icon is correctly `aria-hidden` with the accessible name carried by the parent button's `aria-label` or visible text) — it's a maintainability and visual-consistency problem. Changing icon style later means hunting down and editing path data in N different files by hand.

### Whitespace & styling system

There isn't one consistent system — there are three, mixed within the same components:

- Inline `style={{...}}` objects — used in 20 of 32 `.tsx` files.
- Tailwind `className="..."` — used in 22 of 32 `.tsx` files.
- `<style jsx>` blocks for responsive breakpoints (e.g., the bottom of `DashboardHeader.tsx`).

Most files mix at least two of the three. Tailwind v4 is configured (`@tailwindcss/postcss` in `postcss.config.mjs`), but `src/app/globals.css` is 811 lines of hand-written CSS — a lot of custom CSS to carry alongside a utility framework that's supposed to reduce exactly that. Spacing values in inline styles are hardcoded numbers (`padding: 24`, `margin: 16`, `gap: 12`) rather than referencing Tailwind's scale or a shared spacing token, so "is 16px always the same as 1rem here" isn't guaranteed — it's whatever each component's author typed. Same pattern with color: hex values like `#6b7280`, `#fef3c7`, `#92400e` are written directly in `style={{}}` objects across multiple files rather than pulled from a shared palette, so a brand color change means a repo-wide grep-and-replace, not a one-line token edit.

**Concrete fix direction:** pick one system. Given Tailwind is already configured and the design intent (utility classes) is present in roughly two-thirds of files, migrating the inline-style files to Tailwind classes — and extracting the hand-rolled SVGs into a shared `Icon` component wrapping a real icon set — is less total work than it sounds, because `globals.css`'s 811 lines suggest a lot of what's hand-written is reinventing utilities Tailwind already provides.

### Components, typing, state

- Props are typed (TypeScript strict mode is on — see §6), no `any` spotted in the components reviewed.
- No prop-drilling problems observed; state is appropriately local (`useState` in header/shell) rather than needlessly globalized.
- `ClientForm.tsx`'s default state uses `status: "prospect"` (lowercase) while the Prisma schema's `ClientStatus` enum and the API's validation array use uppercase (`PROSPECT`) — this is a build-blocking type error today, and would be a silent runtime validation failure (every new-client submission rejected) even if the types were loosened. One-line fix, but illustrates that these components were never run against the actual persistence layer they're paired with.

### Accessibility (beyond the header)

Couldn't fully verify color contrast ratios without rendering the app (no screenshot/visual tooling available in this audit), but the hardcoded hex palette includes combinations worth checking manually — e.g., `color: "#92400e"` on `background: "#fef3c7"` (status badge). Keyboard navigation wasn't formally tested; the button-based (not `<div onClick>`) interactive elements throughout the header are a good sign for it working correctly, since real `<button>` elements get keyboard focus and `Enter`/`Space` activation for free.

### Performance

- No `next/image` usage found anywhere — if the app ever adds real images (client logos, avatars, social media post previews), this needs addressing before launch; right now there's nothing to optimize because there are no images, only inline SVG and initials-as-avatar (`avatarStyle` rendering the user's initials — a reasonable choice that sidesteps the image question entirely for now).
- No dynamic `import()` / code-splitting observed — for an app this size (32 `.tsx` files) that's not yet a real problem, but worth revisiting once Pipeline/Inbox-scale features land.
- Bundle size wasn't measured (`pnpm build` doesn't currently complete — see §2.1 — so there's no bundle analysis to report until that's fixed).

### Responsiveness

`DashboardHeader.tsx` has an inline `<style jsx>` responsive block (media queries for `.dh-search`/`.dh-user-text` visibility) — a working pattern, just inconsistent with the Tailwind-first intent elsewhere. Didn't find explicit touch-target sizing checks; icon buttons at 18px/16px/14px SVG size inside presumably-larger button padding should be fine, but wasn't measured against the 44×44px minimum touch-target guideline.

## 5. Backend & API Deep Dive

### Endpoints

REST-style routes under `src/app/api/crm/`: `clients`, `clients/[id]`, `drafts`, `publish`, `brand`, `status`. Naming and HTTP method choice (GET/POST/PATCH/DELETE) are conventional and reasonable. Status codes are mostly right (`201` on create, `404` on not-found) where the code path is reachable at all.

### Correctness — the actual problem

The routes were written against the **real** Prisma Client's method signatures (`prisma.client.findMany({ where, orderBy })`, `.create({ data })`) — that part is correct, modern Prisma usage. They're broken because `src/lib/prisma.ts` isn't a real Prisma Client:

```ts
// src/lib/prisma.ts (current) — abbreviated
export const prisma = {
  client: {
    findMany: async function (model: string, where?: object, orderBy?: object) {
      return [];
    },
    // ...
  },
};
```

Real signature expected by the call sites: `findMany(args: { where?, orderBy? })` — a single options object. The stub's signature is `findMany(model, where, orderBy)` — three positional arguments. Every call site passes a single object as the first argument, which TypeScript correctly flags as a type error against the stub's declared signature, and which — even ignoring types — the stub's body ignores entirely, always returning `[]`. Representative build output:

```
./src/app/api/crm/clients/route.ts:24:38
Type error: Argument of type '{ where: {...}; orderBy: {...}; }' is not
assignable to parameter of type 'string'.

./src/app/api/crm/brand/route.ts
Type error: Expected 0 arguments, but got 1.

./src/generated/prisma/index.ts:4:14
Type error: Operator '|' cannot be applied to types 'string' and 'string'.
  (export const ClientStatus = "PROSPECT" | "ACTIVE" | "PAUSED" | "CHURNED";
   — a type union written where a runtime value was needed)
```

`drafts/route.ts` is a separate, quieter version of the same problem: it imports `prisma` but never calls it. `GET` reads a hardcoded array from `crm.ts`; `POST`/`PATCH` return `{ success: true }` without writing anything, with a comment acknowledging it: *"In v3 with Prisma, we would update/create in the DB. For now, just return success."*

### Auth & authorization

Covered in §2.4 — there is none in effect. No CSRF protection either (no tokens issued, no `SameSite`/origin checks on state-changing routes), though this matters less until real auth exists — right now there's no session to forge.

### Input validation

No schema-validation library (`zod`/`yup`/`joi`) is a dependency. Validation is ad hoc per-route (`if (!draftId || !platform) return 400`), which works for the simple cases checked but gives no systematic protection against malformed nested objects, wrong types that happen to coerce, or missing-field combinations the original author didn't think to check by hand. Worth introducing `zod` (it's a natural fit with TypeScript strict mode, which this project already has) once the routes are otherwise stable.

### Database

- `prisma/schema.prisma` is a genuinely reasonable design — proper relations between `Client`, `ContentDraft`, `PublishJob`, `BrandProfile`; appropriate field types. The problem isn't the schema, it's that nothing executes against it (§2.2).
- Current Prisma CLI pin (`prisma@8.0.0-rc.17` in `devDependencies`) is a pre-release of a different, still-changing CLI product with no `generate` command at all — verified by installing it in isolation and running `--help`. `@prisma/client`/`@prisma/adapter-neon` are correctly pinned to stable `7.10.0`; only the bare `prisma` CLI package drifted.
- `schema.prisma`'s `datasource` block sets `url`/`directUrl` directly, which current Prisma (7+) rejects — connection config needs to move to a `prisma.config.ts` file instead.
- No N+1 query patterns found in the routes reviewed (each route does one `findMany`/`findUnique` per request, no per-row follow-up queries) — this will need re-checking once the routes are wired to a real client, since the stub currently makes query efficiency unobservable.
- No connection pooling strategy wired up despite the right dependency (`@prisma/adapter-neon`) already being installed — it's just never imported/used. On any function-per-request host, a plain `PrismaClient()` without the adapter risks exhausting Neon's connection limit under concurrent load.

### AI / automation integration

This lives entirely in the Python side (`src/smm/`), has its own test suite (pytest, run in CI), and is architecturally sound on paper — a real adapter pattern, moderation layer, workflow orchestration. Two concrete issues found there:

- `src/smm/main.py`'s `compute_engagement_rate` endpoint spawns a subprocess (`subprocess.run(["python3", "-c", f'...{impressions}...{engagements}...'])`) with request values string-interpolated directly into the code string being executed — then computes the identical result directly in Python two lines later as a documented "fallback." The subprocess branch is unnecessary (the fallback already does the same work safely) and is unneeded attack surface for a value that FastAPI already type-coerces to `int` before it reaches this function.
- This FastAPI app has no reachable deployment. `pyproject.toml` declares `[tool.vercel] entrypoint = "smm.main:app"`, but Vercel's Python support doesn't read that location — it needs an `api/` directory or `vercel.json` `builds` config, neither of which exists. The AI engine is not currently callable over HTTP from anywhere, including the dashboard.

### Logging & observability

Essentially absent. A single `console.error` in `src/app/api/graph/route.ts` is the only logging call found across the entire `api/` tree. No structured logging, no Sentry/Datadog/equivalent dependency, no request tracing. For a system whose core value proposition involves an "AI approval gate" making/influencing publishing decisions, not being able to see what happened after the fact is a real gap before launch, not just a nice-to-have.

## 7. Security & Compliance

### OWASP-relevant findings

- **Broken access control (A01):** the headline issue — no auth enforcement on any route (§2.4).
- **Injection:** no SQL injection risk from the Next.js side — Prisma parameterizes queries by default and no raw SQL was found. The Python side's `subprocess.run(["python3", "-c", f"...{value}..."])` pattern (§5, AI integration) is a real code-construction-via-string-interpolation smell, mitigated somewhat by FastAPI's type coercion but still worth removing on principle — it's unnecessary regardless of exploitability, since the safe path already exists two lines below it.
- **Security misconfiguration:** no CORS policy, no CSP, no security headers (`X-Frame-Options`, `Strict-Transport-Security`, etc.) configured anywhere — `next.config.ts` has no `headers()` function at all. For an internal dashboard this is lower-stakes than for a public-facing site, but given finding §2.4 (no auth), this dashboard is currently effectively public.
- **Rate limiting:** none. No rate-limiting dependency, no middleware-based throttling. Combined with the open routes in §2.4, nothing currently stops automated abuse of any endpoint, including the publish-simulation endpoint.
- **Secrets management:** clean — no hardcoded credentials found repo-wide beyond the already-documented, clearly-labeled demo login stub. `.env` is correctly gitignored.
- **CSRF:** no tokens, no origin checks on state-changing routes — low current impact only because there's no session to forge yet (§2.4 again); will matter the moment real auth lands.

### Data privacy

The data model (`Client`: name, email, phone, company) is standard B2B CRM PII — nothing here suggests special-category data, but there's currently no documented data-retention policy, no visible mechanism for data deletion requests, and (per §2.4) no access control around who can read it. If this product will have EU or California users, GDPR/CCPA data-subject-request handling isn't built yet — worth flagging now, before the schema and routes are locked in, since retrofitting deletion/export flows is cheaper before launch than after.

### Third-party integrations

`META_ACCESS_TOKEN`/`META_PAGE_ID` exist in `.env.example` but aren't referenced anywhere in the Next.js source, and no OAuth flow or webhook-verification code was found in either codebase. The "connect your social accounts" part of this product doesn't exist yet in any form — not broken, just not started.

## 9. Quick Wins

Low effort, immediately visible improvement — do these even before the P0 list if you want a fast morale/credibility win:

- Fix the root `package.json`/lockfile mismatch (`pnpm install --lockfile-only` after removing the stray `next` dependency) — 5 minutes, unblocks `pnpm install --frozen-lockfile` at the repo root.
- Fix `ClientForm.tsx`'s `status: "prospect"` → `"PROSPECT"` casing — one line, removes a silent form-submission failure once persistence is real.
- Replace the hardcoded notification list in `DashboardHeader.tsx` with an honest empty state until real notification data exists — a few lines, removes a "this app is lying to me" moment for the first real user.
- Delete the committed `allowBuilds: { unrs-resolver: set this to true or false }` placeholder from `pnpm-workspace.yaml` — actually answer it or remove the file.
- Add `pnpm build` as a required GitHub Actions check — the single highest-leverage change in this entire report relative to effort; it would have caught nearly everything in §2 automatically, for every PR, forever, for about an hour of setup.
